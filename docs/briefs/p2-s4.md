# Second pass, S4: the synthetic world, now against the real features

Paths: `src/features/synth/**`, `seed/**`, `evals/**` except `evals/prompt-lab/**`, `scripts/sim.ts`, `scripts/seed.ts`. Spec: `docs/specs/synthetic-world.md`, `docs/specs/demo-script.md`.

Every feature is merged now. The simulator has only ever run against stand-ins (`fake-engine.ts`). Nobody has yet seen one person travel the whole product. Block A is that journey, as a test.

## Block A: one journey through the real features (report after this)

1. An end-to-end test, `src/features/synth/journey.test.ts`, on PGlite with `loadJobFixtures` and `setLlmFake`. The fake answers by `purpose` with outputs shaped like each prompt spec's worked examples; it stands in for the model only. Everything else is the real code, called the way production calls it:
   - a persona's simulated interview through `@/features/interview` (`startInterview`, `submitTurn`, `settleInterview`), then the draft card from `@/features/card`, approval and pool opt-in;
   - queue jobs run with `runReadyJobs` and the real job definitions from `src/worker/registry.ts`, until the queue is empty;
   - a Need Card drafted for a masked demo company through `@/features/needs`, eligibility and the person's feed from `@/features/matching`, pool evidence recomputed;
   - `draftDailyDigests`, then the organiser's decisions and publish, the company page payload, "ask to meet", the person's acceptance, and the reveal. These live in `src/features/picks` and `src/features/intros` behind route handlers; call the route handlers with real `Request` objects and sessions, as the streams' own route tests do.
   Assert at each step what a person would see: the card has signals with evidence that resolves to the person's own sentences; the feed has postings with reasons; the organiser's queue has the pick; nothing reaches the company page before approval and publish; the company payload has no name, no language and no input mode before acceptance and exactly the agreed fields after; an audit row exists for every step.
2. When the journey breaks at a boundary between features, find the cause. You may fix a bug in another feature's code when the fix is small (about 20 lines) and your test proves it; make each such fix its own commit whose message starts with "Integration fix:" and names the feature. Anything larger: leave a clearly named failing step marked `it.fails` or skipped with the diagnosis, and report it. Other builders are changing those features right now, so keep such fixes surgical.
3. `runSimulatedInterview` and `seedDemo` use the real features by default; `--fake` keeps the stand-in. Delete what the real features made obsolete (`FeatureNotReadyError` paths that can no longer happen).

## Block B: decisions from the review

4. Labelling (`docs/LEAD-DECISIONS.md`, 14 Nov): in the same update that sets `synthetic: true`, clear `purgeAfter` and `liveDemo`. Test that a simulated person is never due for purging and that a person the simulator failed to label is.
5. Seeded history is written by actor `system` with `seeded: true` in the audit detail; the seed never writes an approval as if an organiser had made it.
6. Create `src/features/synth/index.ts` exporting `resetDemoFromSnapshot(db)` exactly as `docs/FEATURE-API.md` describes it (a stub with that signature exists on main; replace its body). Today's picks drafted during a reset must not wait on a model for more than the reasons call's own deadline.
7. The simulated-interview line (`SIMULATED_TRANSCRIPT_LINE`) is returned with the transcript wherever the synthetic world hands a transcript to a view, and metric 13b uses keywords specific enough not to fire on ordinary words (the review's finding).

## Block C: ready for the real model

8. `npm run sim -- --n <k> --report <path>` and `npm run seed` print, per interview and in total: model calls by purpose, failures by reason, time waited for a rate-limit slot, and wall time, read from the `llm_call` rows (`attempts`, `queued_ms`). The lead will run these against the real model with one process and needs to see where time goes. `npm run seed -- --snapshot` writes the snapshot after a successful seed.
